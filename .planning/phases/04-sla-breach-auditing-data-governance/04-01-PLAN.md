# Plan 04-01: SLA Breach Tracking Metadata & Immutability Governance

## Objective

Package automated SLA breach field updates for declarative milestone violation triggers ([GOV-01](file:///home/elsner/Salesforce/SalesforceProject/.planning/REQUIREMENTS.md)), create the enterprise `Bypass_Case_Lock` Custom Permission, and extend validation rule [VR_Case_Lock_Customer_And_SLA_Data](file:///home/elsner/Salesforce/SalesforceProject/force-app/main/default/objects/Case/validationRules/VR_Case_Lock_Customer_And_SLA_Data.validationRule-meta.xml) to enforce strict immutability across customer intake and SLA tracking fields ([GOV-02](file:///home/elsner/Salesforce/SalesforceProject/.planning/REQUIREMENTS.md)).

## Context

- `04-CONTEXT.md` Decision D-01: Package standard Workflow Field Updates in `force-app/main/default/workflows/Case.workflow-meta.xml` (`Set_SLA_Breached_True` and `Set_SLA_Violation_Yes`) following the existing `ChangePriorityToHigh` pattern, enabling Entitlement Process milestone breach actions.
- `04-CONTEXT.md` Decision D-02: Add `ISCHANGED(SLAViolation__c)` to the existing locked fields in `VR_Case_Lock_Customer_And_SLA_Data`.
- `04-CONTEXT.md` Decision D-03: Create Custom Permission `Bypass_Case_Lock` in `force-app/main/default/customPermissions/Bypass_Case_Lock.customPermission-meta.xml` and enforce `$Permission.Bypass_Case_Lock` bypass gate in `VR_Case_Lock_Customer_And_SLA_Data`. All standard users and administrators are locked out of altering intake and SLA telemetry unless explicitly granted `Bypass_Case_Lock`.

<threat_model>
### Threat Modeling & Risk Register

| Threat ID | Category | Description | Severity | Mitigation Strategy |
|-----------|----------|-------------|----------|---------------------|
| T-04-01 | Data Tampering / Governance | Support agents or unauthorized users alter `SLA_Breached__c` or `SLAViolation__c` to artificially suppress breach reports. | High | Enforce validation rule `VR_Case_Lock_Customer_And_SLA_Data` on `ISCHANGED(SLA_Breached__c)` and `ISCHANGED(SLAViolation__c)`. |
| T-04-02 | Operational Lockout | Legitimate automated integrations or authorized data migration scripts are blocked from updating Cases. | Medium | Gate the validation rule with `NOT($Permission.Bypass_Case_Lock)` so authorized profiles/permission sets can bypass when strictly required. |
| T-04-03 | Deployment / Metadata Dependency | Validation rule fails deployment if referenced Custom Permission is missing or misnamed. | High | Deploy `Bypass_Case_Lock.customPermission-meta.xml` atomically before or alongside the validation rule. |
| T-04-04 | Milestone Trigger Incompatibility | Workflow field updates fail to fire or reevaluate incorrectly on milestone violation. | Low | Configure `operation: Literal`, `reevaluateOnChange: false`, and `notifyAssignee: false` aligned with standard milestone workflow actions. |
</threat_model>
